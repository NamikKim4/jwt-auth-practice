# JWT 포털 (로그인 + 게시판 웹사이트 실습)

회원가입 → 로그인 → 로그인한 사람만 쓸 수 있는 게시판, 이 흐름을 JWT(JSON Web Token) 방식으로 직접 구현해본 실습이에요.
글 목록 보기는 로그인 없이도 가능하지만, 글쓰기/수정/삭제는 로그인해야 하고, 본인이 쓴 글만 수정/삭제할 수 있어요.

## 파일 구조

기능별로 파일을 나눴어요.

```
jwt-auth-practice/
├── .env                  # 진짜 비밀값 (git에 안 올라감)
├── .env.example          # 비밀값 견본 (git에 올라감, 값은 비어있음)
├── .gitignore
├── docker-compose.yml
app/
├── main.py              # 앱 시작점. 라우터 연결 + 서버 시작 시 DB 준비 + 날씨 백그라운드 작업 시작
├── config.py             # 환경변수 설정값 모음
├── database.py            # PostgreSQL 연결 함수 + 테이블 생성
├── mongo.py                # MongoDB 연결 (날씨 + 게시글 백업, PostgreSQL과 별개)
├── models.py               # 요청/응답 데이터 모양 (Pydantic)
├── security.py              # 비밀번호 해시, JWT 생성/검증, 로그인 필수 처리
├── excel_utils.py            # 리스트 → .xlsx 변환 공용 함수
├── seed_data.py           # 서버 시작 시 상품후기 샘플 캐릭터 자동 등록
├── weather_fetcher.py       # 외부 API에서 날씨 가져오기 + 30분마다 반복하는 백그라운드 작업
├── backup_sync.py            # PostgreSQL 게시글을 MongoDB로 복사 + 1시간마다 반복하는 백그라운드 작업
├── repositories/               # DB 접근은 여기에만 있음 (users~products는 SQL, weather/backup은 MongoDB 쿼리)
│   ├── users.py
│   ├── posts.py
│   ├── comments.py
│   ├── files.py
│   ├── products.py
│   ├── weather.py
│   └── backup.py
├── routers/                    # 요청/응답 처리만
│   ├── auth.py                     # /signup, /login, /me
│   ├── posts.py                      # 게시판 + 댓글
│   ├── account.py                      # 비밀번호 변경, 회원 탈퇴
│   ├── files.py                          # 자료실 업로드/다운로드
│   ├── export.py                           # 엑셀 출력
│   ├── activity.py                           # 내 활동
│   ├── products.py                             # 상품등록 및 후기
│   ├── admin.py                                  # 관리자: 회원 관리, 사이트 현황
│   ├── weather.py                                  # 날씨 조회/수동 등록
│   └── backup.py                                     # 게시글 백업 상태 조회/수동 실행
├── templates/index.html        # 프론트엔드 화면 골격 (HTML만)
└── static/                       # 프론트엔드 CSS/JS
    ├── css/style.css                 # 디자인 전체
    └── js/app.js                       # 화면 동작 로직 전체
```

**프론트엔드도 파일을 나눴어요** (원래는 `index.html` 하나에 HTML+CSS+JS가 다 들어있었는데, 보기 불편해서 분리했어요):
- `templates/index.html` — 화면에 뭐가 있는지(구조)만 담당
- `static/css/style.css` — 어떻게 생겼는지(디자인)만 담당
- `static/js/app.js` — 클릭했을 때 뭐가 일어나는지(동작)만 담당

`main.py`에 `app.mount("/static", ...)`를 추가해서, `/static/css/style.css`, `/static/js/app.js` 경로로 파일을 그대로 내려줄 수 있게 했어요. `index.html`은 이제 `<link>`/`<script src="...">` 태그로 이 두 파일을 불러오기만 해요.

**왜 이렇게 나눴나:**
- `main.py`가 짧아져서 "이 앱에 뭐가 있는지" 한눈에 보여요 (라우터 연결만 보임)
- SQL 쿼리는 `repositories/`에만 있어서, 나중에 테이블 구조가 바뀌어도 그 파일만 고치면 돼요
- `routers/`는 HTTP 요청/응답 처리만 담당하고, 실제 DB 작업은 `repositories/`에 위임해요 (역할 분리)
- 이런 식으로 계층을 나누는 걸 실무에서 "레이어드 아키텍처"라고 불러요

## 환경변수(.env) 설정

비밀번호, JWT 서명 키, 관리자 코드 같은 값들은 코드에 직접 적어두지 않고 `.env` 파일에 따로 빼놨어요. `.env`는 `.gitignore`에 들어있어서 git에는 절대 올라가지 않아요 — 대신 값이 비어있는 견본 파일 `.env.example`만 커밋돼요.

**처음 실행하기 전에 한 번만 해주면 돼요:**

```
cd "C:\docker practice\jwt-auth-practice"
copy .env.example .env
```

그다음 `.env` 파일을 열어서 값들을 원하는 대로 바꿔주세요. 특히 `JWT_SECRET_KEY`는 아무거나 길고 예측 불가능한 문자열로 바꾸는 걸 추천해요 (터미널에서 `python3 -c "import secrets; print(secrets.token_hex(32))"`로 만들 수 있어요). `ADMIN_SIGNUP_CODE`는 회원가입할 때 "관리자로 가입"을 선택하면 입력해야 하는 코드예요.

`docker compose`는 같은 폴더에 있는 `.env` 파일을 자동으로 읽어서, `docker-compose.yml` 안의 `${JWT_SECRET_KEY}` 같은 부분에 채워 넣어줘요.

**왜 이렇게 나눴나:** 예전엔 비밀번호랑 관리자 코드가 `docker-compose.yml`에 그대로 텍스트로 적혀있었어요. 이 파일은 git에 커밋되는 파일이라, 그대로 GitHub에 올리면 누구나 그 값들을 볼 수 있게 돼요. 실제 서비스였다면 심각한 보안 문제죠. `.env`로 분리하면 "코드(공개돼도 되는 것)"와 "비밀값(공개되면 안 되는 것)"이 깔끔하게 나뉘어요.

## 실행 방법

```
cd "C:\docker practice\jwt-auth-practice"
docker compose up --build
```

(`.env` 파일이 없다면 위 "환경변수(.env) 설정"을 먼저 봐주세요.)

브라우저에서 http://localhost:8001 접속하면 한글 로그인/회원가입 화면이 떠요.
API 문서만 따로 보고 싶으면 http://localhost:8001/docs (Swagger UI)로 접속하면 돼요.

게시판 아래로 메뉴가 더 늘었어요.

- **🌤️ 날씨** — 외부 API에서 30분마다 자동으로 가져오는 날씨 기록 + 수동 등록. 아래에서 따로 자세히 설명해요
- **🎁 상품등록 및 후기** — 사진 + 설명으로 남기는 리뷰 게시판. 아래에서 따로 자세히 설명해요
- **⚙️ 계정관리** — 비밀번호 변경, 회원 탈퇴(작성한 글/댓글/파일은 남아있어요)
- **🗂️ 자료실** — 파일 업로드/다운로드/삭제 (최대 20MB). 업로드된 파일은 도커 볼륨(`uploads_data`)에 저장돼서, 컨테이너를 껐다 켜도 안 사라져요
- **📊 엑셀 출력** — 게시글 목록 / 자료실 목록을 `.xlsx` 파일로 바로 다운로드
- **🕓 내 활동** — 내가 쓴 글 / 댓글 / 올린 파일을 한 화면에 모아보기
- **🛡️ 관리자** — 첫 가입자(또는 관리자 코드로 가입한 사람)만 보이는 메뉴. 전체 회원/글/파일/후기/날씨 현황과 회원 관리. 아래에서 따로 자세히 설명해요

파일은 실제 파일 자체(바이너리)는 서버 디스크(볼륨)에 저장하고, DB에는 "누가 언제 어떤 이름으로 올렸는지"라는 메타데이터만 저장해요. 실무에서도 대용량 파일은 이렇게 파일시스템(또는 S3 같은 스토리지)과 DB를 분리해서 관리해요.

## 게시판 퀄리티 업그레이드

- **댓글**: 게시글마다 댓글을 달고, 본인이 쓴 댓글만 삭제할 수 있어요. `posts`와 `comments` 테이블이 1:N 관계로 연결돼있어요 (게시글 하나 지우면 댓글도 같이 지워지도록 `ON DELETE CASCADE` 설정)
- **조회수**: 글을 열어볼 때마다 1씩 증가해요
- **검색 + 정렬**: 제목으로 검색하고, 최신순/조회수순으로 정렬해서 볼 수 있어요
- **디자인**: 아바타(이름 이니셜 + 자동 색상), "n분 전"처럼 사람이 읽기 편한 시간 표시, 목록에 미리보기 텍스트, 호버 시 카드가 살짝 떠오르는 효과 등을 추가했어요
- **표 + 페이지네이션 레이아웃**: 실제 쇼핑몰/커뮤니티 사이트 게시판처럼, 상단 배너(히어로) + 번호/구분/제목/작성자/등록일/조회수 표 형태로 바꿨어요. 한 페이지에 10개씩만 보여주고, 아래 번호 버튼으로 페이지를 이동해요. 백엔드에서 `LIMIT`/`OFFSET`으로 필요한 만큼만 DB에서 가져오기 때문에, 글이 아무리 많아져도 목록 화면이 느려지지 않아요

## 날씨 (외부 API + MongoDB)

게시판 바로 아래에, 30분마다 외부에서 자동으로 날씨를 받아와서 보여주는 메뉴를 추가했어요. 지금까지 만든 다른 기능들이랑 다른 점이 두 가지예요: (1) 데이터가 사용자 입력이 아니라 **외부 API에서 자동으로** 들어온다는 것, (2) 저장하는 곳이 PostgreSQL이 아니라 **MongoDB(NoSQL)**라는 완전히 다른 종류의 데이터베이스라는 것.

- **데이터 출처**: [Open-Meteo](https://open-meteo.com) 라는 무료 날씨 API를 써요. 회원가입도, API 키 발급도, 카드 등록도 필요 없는 완전 무료 API라 돈이 나갈 일이 전혀 없어요.
- **자동 수집**: 서버가 켜지면 `weather_fetcher.py`의 `weather_background_loop()`가 백그라운드에서 계속 돌면서, `WEATHER_FETCH_INTERVAL_SECONDS`(기본 1800초 = 30분)마다 한 번씩 날씨를 새로 가져와서 저장해요. `asyncio.create_task()`로 띄운 작업이라, 다른 API 요청 처리랑 동시에 돌아가요.
- **수동 등록**: 자동 수집 말고, 로그인한 사람이 직접 "기온 몇 도, 무슨 날씨였다" 하고 손으로 기록을 남길 수도 있어요. 자동으로 들어온 기록은 "🤖 자동수집" 배지, 사람이 직접 남긴 기록은 "📝 (아이디)" 배지로 구분돼서 표에 표시돼요.
- **왜 PostgreSQL 대신 MongoDB를 썼나**: 회원/게시글/파일처럼 "제목, 작성자, 내용" 같은 구조가 고정된 데이터는 관계형 DB(PostgreSQL)가 잘 맞아요. 근데 외부 API에서 그대로 받아오는 데이터는 나중에 API가 필드를 추가/변경할 수도 있고, 굳이 미리 정해진 테이블 스키마에 맞출 필요가 없어서, 스키마 없이 문서(JSON과 비슷한 형태) 그대로 저장하는 MongoDB를 대신 써봤어요. `mongo.py`가 연결을 담당하고, `repositories/weather.py`가 실제 저장/조회를 담당해요 (PostgreSQL 쪽의 `database.py`/`repositories/*.py`와 똑같은 역할 분리 구조예요).
- **완전히 별도의 컨테이너**: `docker-compose.yml`에 `mongo`라는 컨테이너가 하나 더 늘었어요. 기존 `db`(PostgreSQL) 컨테이너랑은 완전히 독립적으로 떠 있는 별개의 DB예요. 데이터도 별도 볼륨(`mongodata`)에 저장돼서, `docker compose down`을 해도 사라지지 않아요.
- **위치 설정**: 기본값은 서울(위도/경도)이에요. `.env`의 `WEATHER_CITY_NAME`, `WEATHER_LAT`, `WEATHER_LON` 값을 바꾸면 다른 지역 날씨로 바꿀 수 있어요.

## 상품등록 및 후기

사진 한 장 + 설명을 남기면 카드 형태로 쌓이는, 리뷰 게시판이에요. 게시판과 구조는 비슷하지만 이미지가 들어간다는 점이 달라요.

- 서버가 처음 켜질 때 `seed_data.py`가 예시 후기 5개를 자동으로 등록해요(이미 있으면 다시 넣지 않아요). 캐릭터 이미지는 외부에서 가져온 게 아니라, 저작권 문제 없이 코드로 직접 그린 원(눈)+선(입) 조합의 간단한 SVG 캐릭터예요
- 이미지는 별도 파일로 저장하지 않고, `data:image/svg+xml;base64,...` 같은 문자열 그대로 DB의 `products.image_data` 컬럼(TEXT)에 저장해요. 이렇게 하면 자료실처럼 디스크 경로를 따로 관리할 필요가 없어서 구조가 단순해지지만, 이미지가 많아지고 커질수록 DB 용량이 그만큼 커진다는 단점이 있어요. 그래서 업로드 용량을 3MB로 제한해뒀어요(실무라면 자료실처럼 파일시스템이나 S3에 저장하는 쪽을 권장해요)
- 로그인한 사람은 누구나 사진을 골라 자기 후기를 등록할 수 있고, 본인이 쓴 후기만 수정/삭제할 수 있어요(서버에서도 작성자를 다시 확인해요)

## 관리자 기능

회원가입 화면에서 **계정 유형(🙂 일반 사용자 / 🛡️ 관리자로 가입)**을 직접 고를 수 있어요. "관리자로 가입"을 선택하면 **관리자 코드** 입력칸이 나타나고, 이 코드가 서버에 설정된 값(`ADMIN_SIGNUP_CODE` 환경변수, 기본값 `admin1234`)과 일치해야만 관리자 계정으로 만들어져요. 코드가 틀리면 가입이 거부돼요 — 아무나 코드 없이 관리자가 될 수는 없어요.

(안전장치로, 사이트에 회원이 정말 아무도 없는 최초 1명은 코드를 몰라도 자동으로 관리자가 돼요. 관리자가 한 명도 없는 상태를 막기 위한 예외예요.)

실제로 배포할 땐 `.env` 파일의 `ADMIN_SIGNUP_CODE` 값을 본인만 아는 값으로 꼭 바꿔서 쓰세요 (자세한 건 위쪽 "환경변수(.env) 설정" 참고).

관리자로 로그인하면 사이드바 맨 아래에 **🛡️ 관리자** 메뉴가 보여요(일반 회원에게는 아예 안 보여요). 이 화면에서:

- 전체 회원 수 / 게시글 수 / 파일 수 / 상품후기 수를 한눈에 확인할 수 있어요
- 전체 회원 목록을 표로 보고, 각자 글/파일을 몇 개 남겼는지 볼 수 있어요
- 본인 계정을 제외한 다른 회원 계정을 삭제할 수 있어요(그 사람이 쓴 글/댓글/파일은 그대로 남아요 — 계정관리의 회원 탈퇴와 동일한 정책)

권한 체크는 `security.py`의 `require_admin` 의존성이 담당해요. `get_current_user`로 로그인 여부를 먼저 확인한 다음, `current_user["is_admin"]`이 아니면 403 에러를 내는 방식이라, 프론트엔드에서 메뉴를 숨겨도 API를 직접 호출하는 건 서버에서 한 번 더 막혀요.

관리자 화면 안에는 **게시글 백업(PostgreSQL → MongoDB)** 카드도 있어요. 아래 "PostgreSQL → MongoDB 백업" 항목에서 자세히 설명해요.

## PostgreSQL → MongoDB 백업

서로 다른 두 데이터베이스(PostgreSQL, MongoDB) 사이에서 데이터를 옮기는 걸 보여주는 기능이에요. **게시글(posts)** 을 예시로 골라서, PostgreSQL에 있는 원본은 그대로 두고 **같은 내용을 MongoDB에도 복사**해둬요.

- **원본은 안 건드림**: PostgreSQL의 `posts` 테이블은 평소처럼 그대로 쓰여요. 백업은 "복사"만 하지, 원본을 지우거나 옮기는(이관) 게 아니에요.
- **자동 백업**: `backup_sync.py`의 `backup_background_loop()`가 서버 켜져있는 동안 계속 돌면서, `BACKUP_SYNC_INTERVAL_SECONDS`(기본 3600초 = 1시간)마다 게시글 전체를 다시 MongoDB로 복사해요. 날씨 자동 수집(`weather_fetcher.py`)이랑 똑같은 구조의 백그라운드 작업이에요.
- **수동 백업**: 관리자 화면에 "🔄 지금 백업 실행" 버튼이 있어서, 1시간을 안 기다리고 바로 실행시킬 수도 있어요.
- **중복 없이 갱신(upsert)**: 자동이든 수동이든 여러 번 실행해도 게시글이 중복으로 쌓이지 않아요. PostgreSQL의 글 번호(`id`)를 MongoDB 문서의 `_id`로 그대로 써서, 같은 글이면 덮어쓰기(갱신)만 되게 만들었어요 — 이런 저장 방식을 "upsert"(update + insert)라고 불러요.
- **저장 위치**: MongoDB의 `backup_db` 데이터베이스, `posts_backup` 컬렉션이에요. 날씨 데이터가 있는 `weather_db`랑은 다른 데이터베이스로 분리해뒀어요 (용도가 다른 데이터를 한 덩어리에 안 섞으려고요).
- **왜 이런 걸 만드나**: 실무에서도 "평소에 쓰는 DB(운영 DB)는 그대로 두고, 다른 종류의 저장소에 주기적으로 복사본을 만들어두는" 패턴을 백업/재해복구(DR) 목적으로 많이 써요. 여기서는 같은 서버 안에서 PostgreSQL → MongoDB로 복사하는 걸로 단순화해서 그 패턴을 보여줘요.

## 화면 구성

로그인하면 상단 헤더 + 왼쪽 사이드바 메뉴가 있는, 사이트 같은 레이아웃으로 들어가요 (홈페이지 서비스들 흔히 쓰는 구조예요).

- **상단 헤더**: 사이트 이름, 오늘 날짜, 로그인한 아이디, 로그아웃 버튼
- **왼쪽 사이드바**: 🏠 홈 / 📋 게시판 / 🎁 상품등록 및 후기 / ⚙️ 계정관리 / 🗂️ 자료실 / 📊 엑셀 출력 / 🕓 내 활동 / 👤 내 정보
- **홈**: 인사말 + 전체 게시글 수, 글쓰기 바로가기, 내 정보 바로가기 카드
- **게시판**: 목록(표+페이지네이션)/상세/글쓰기/수정/삭제 + 검색 + 정렬(최신순/조회수순) + 조회수 + 댓글
- **상품등록 및 후기**: 카드 목록/상세/등록/수정/삭제, 사진 미리보기
- **내 정보**: `/me`가 보여주는 내 계정 정보 카드

## 테스트 순서 (화면으로)

1. "회원가입" 탭에서 아이디/비밀번호 입력 후 "계정 만들기"
2. 자동으로 로그인 탭으로 넘어가면 방금 만든 계정으로 로그인
3. 로그인되면 게시판 화면으로 넘어가요
4. "✏️ 글쓰기"로 제목/내용 넣고 등록 → 목록에 바로 보여요
5. 글 클릭하면 상세 화면. 내가 쓴 글이면 "수정"/"삭제" 버튼이 보여요
6. 다른 계정으로 로그인해서 남의 글을 열어보면 수정/삭제 버튼이 안 보이는 것도 확인해보세요 (서버에서도 한 번 더 작성자 체크를 해서, 버튼을 억지로 보이게 해도 실제로는 막혀요)
7. "로그아웃" 누르면 다시 로그인 화면으로 돌아가고, 새로고침해도 로그인은 유지돼요

## 화면 접근성 관련 신경 쓴 부분

- 모든 입력창에 `<label>`을 제대로 연결해서, 스크린리더로도 "아이디 입력창"처럼 읽혀요.
- 비밀번호 입력창에 "표시/숨김" 버튼을 넣어서, 입력한 값을 확인할 수 있어요.
- 포커스(Tab 키로 이동했을 때) 시 테두리가 뚜렷하게 보이도록 했어요.
- 에러/성공 메시지는 `aria-live` 영역이라, 스크린리더 사용자에게도 즉시 안내돼요.
- 로그인/회원가입 탭은 키보드로도 전환 가능해요.

## 데이터는 어디에 남고, 컨테이너를 껐다 켜도 사라지지 않을까?

글/댓글/회원정보 같은 DB 데이터는 `db` 컨테이너(PostgreSQL) 안에 저장돼요. 그런데 컨테이너 자체는 언제든 지워질 수 있는 "일회용"에 가까운 존재라서, 데이터가 컨테이너 안에만 있으면 컨테이너를 지우는 순간 데이터도 같이 날아가요. 그래서 도커에서는 컨테이너 바깥, 즉 "볼륨(volume)"이라는 별도 저장 공간에 실제 데이터를 두고, 컨테이너는 그 볼륨을 연결(마운트)해서 쓰기만 해요. 컨테이너를 지웠다가 새로 만들어도, 같은 볼륨을 다시 연결하면 데이터는 그대로예요.

- `docker compose stop` / 터미널에서 `Ctrl+C`: 컨테이너를 멈추기만 해요. 컨테이너가 사라지는 게 아니라서 데이터는 원래도 안전해요.
- `docker compose down`: 컨테이너를 아예 지워요. 이때 볼륨에 연결이 안 돼있던 데이터는 컨테이너와 함께 사라지고, 볼륨에 있는 데이터는 남아요.

`docker-compose.yml`을 다시 보니 `web` 서비스(자료실 파일)는 `uploads_data`라는 볼륨에 연결돼있었는데, `db` 서비스(PostgreSQL)에는 볼륨 연결이 빠져있었어요. 그래서 그동안 `docker compose down` 후 다시 `up`할 때마다 회원가입/게시글/댓글/후기처럼 DB에 저장되는 데이터는 전부 초기화되고 있었을 거예요(상품후기 캐릭터 30개는 서버가 켜질 때 자동으로 다시 채워지는 로직이라 티가 안 났을 수 있어요). 지금 `pgdata`라는 볼륨을 추가해서 `db` 컨테이너의 데이터 폴더(`/var/lib/postgresql/data`)를 여기 연결해뒀으니, 앞으로는 `down`을 해도 회원/게시글/댓글/후기 데이터가 안전하게 남아있어요.

```yaml
db:
  volumes:
    - pgdata:/var/lib/postgresql/data   # 새로 추가됨
```

참고로 이미 `down`을 여러 번 했다면 지금부터는 안전하지만, 그 이전에 만들었던 계정/게시글은 이미 사라졌을 수 있어요.

## 토큰 저장 방식에 대한 참고

로그인 토큰을 브라우저 `localStorage`에 저장했어요. 그래서 새로고침해도 로그인이 유지돼요.
다만 실무에서는 XSS 공격에 취약할 수 있어서, `httpOnly` 쿠키 방식을 더 권장해요. 여기서는 학습용으로 가장 단순한 방식을 썼어요.

## 핵심 개념 정리

- **비밀번호는 절대 그대로 저장하지 않는다**: `passlib`의 bcrypt로 해시해서 저장해요. 해시는 되돌릴 수 없는 단방향 변환이라, DB가 통째로 유출돼도 원래 비밀번호는 알 수 없어요.
- **JWT 토큰 구조**: `{"sub": "사용자이름", "exp": 만료시각}` 같은 정보를 SECRET_KEY로 서명해서 만든 문자열이에요. 서버는 이 서명을 검증만 하면 되기 때문에, 매 요청마다 DB에서 세션을 조회할 필요가 없어요.
- **`Depends(get_current_user)`**: FastAPI의 의존성 주입 기능. `/me`처럼 로그인이 필요한 엔드포인트 앞에 이걸 붙이면, 토큰 검증을 자동으로 먼저 처리해줘요.
- **SECRET_KEY**: 지금은 코드에 대충 박아뒀는데, 실무에서는 이것도 `.env`로 분리하고 절대 커밋하면 안 되는 값이에요.
