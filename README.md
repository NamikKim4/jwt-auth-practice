# JWT 포털 (로그인 + 게시판 웹사이트 실습)

JWT 인증을 코드로 직접 짜보면서 이해하고 싶어서 시작한 프로젝트예요. 회원가입 → 로그인 → 로그인한 사람만 글을 쓸 수 있는 게시판, 이 기본 흐름만 만들어보려고 했는데 하다 보니 계속 뭔가를 붙이게 돼서 지금은 날씨, 상품후기, 미니게임, 알림 같은 곁가지 기능들까지 꽤 늘어났어요. 처음 목표였던 "JWT 이해하기"는 이미 끝났고, 그 뒤로는 FastAPI 레이어 구조, PostgreSQL/MongoDB 같이 써보기, 도커 볼륨 등 손대는 김에 익혀보고 싶었던 것들을 하나씩 실습해본 결과물에 가까워요.

글 목록은 로그인 없이도 볼 수 있지만, 글쓰기/수정/삭제는 로그인해야 하고 본인 글만 수정·삭제할 수 있어요.

## 실행 방법

```
cd "C:\docker practice\jwt-auth-practice"
docker compose up --build
```

처음 실행하는 거라면 `.env` 파일부터 만들어야 해요 (없으면 서버가 아예 안 켜져요):

```
copy .env.example .env
```

만들고 나서 `.env`를 열어서 값들을 바꿔주면 돼요. `JWT_SECRET_KEY`는 아무 문자열이나 넣지 말고 길고 예측 안 되는 값으로 바꾸는 게 좋아요 — 터미널에서 `python3 -c "import secrets; print(secrets.token_hex(32))"` 치면 하나 뽑아줘요. `ADMIN_SIGNUP_CODE`는 회원가입할 때 "관리자로 가입"을 고르면 물어보는 코드고요.

다 되면 브라우저에서 http://localhost:8001 열면 돼요. API만 따로 궁금하면 http://localhost:8001/docs 로 들어가면 Swagger 문서가 자동으로 떠요.

끝낼 땐:
```
docker compose down
```

## DB 안 내용을 직접 눈으로 보고 싶을 때

`http://localhost:5435`나 `http://localhost:27018`을 브라우저에 쳐도 아무것도 안 떠요. 이 포트들은 PostgreSQL/MongoDB가 쓰는 포트인데, 얘네는 브라우저가 쓰는 HTTP가 아니라 자기들만의 통신 방식을 쓰기 때문이에요. 그래서 웹사이트처럼 열리지 않고, 전용 프로그램으로 접속해야 해요.

Oracle로 치면 SQL Developer 같은 역할을 하는 걸 이 프로젝트엔 docker-compose에 미리 같이 띄워뒀어요.

- **pgAdmin** (PostgreSQL용): `docker compose up` 하면 같이 켜지고, http://localhost:5050 접속 → `.env`의 `PGADMIN_EMAIL` / `PGADMIN_PASSWORD`로 로그인 → 서버 등록 화면에서 Host `db`, Port `5432`, DB이름/계정은 `.env`의 `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` 입력하면 테이블 목록, 컬럼, 데이터를 클릭클릭 해서 볼 수 있어요.
- **mongo-express** (MongoDB용): http://localhost:8081 접속 → 브라우저 기본 로그인창에 `.env`의 `MONGO_EXPRESS_USERNAME` / `MONGO_EXPRESS_PASSWORD` 입력하면 컬렉션(posts_backup, weather_backup)과 그 안 문서들을 바로 볼 수 있어요.

둘 다 완전 무료 오픈소스 이미지라 회원가입이나 카드 등록 없이 그냥 켜져요. 개발용 도구라 로그인 정보가 단순해도 되지만, 그래도 `.env`에서 기본값(`change-this-password`)은 바꿔서 쓰는 걸 추천해요.

## 왜 .env를 따로 뒀나

원래는 비밀번호, 관리자 코드 같은 값들을 그냥 `docker-compose.yml`에 텍스트로 박아놨었어요. 근데 이 파일은 git에 커밋되는 파일이라, 그대로 GitHub에 올리면 그 값들이 다 공개돼버려요. 뒤늦게 그게 문제라는 걸 깨닫고 `.env`로 옮겼어요. `.env`는 `.gitignore`에 넣어서 git에 절대 안 올라가고, 대신 값이 비어있는 `.env.example`만 커밋해서 "어떤 값들이 필요한지"는 알 수 있게 해뒀어요.

`main.py`가 뚱뚱해지는 게 싫어서 라우터 연결만 남기고 나머지는 다 빼냈어요. `routers/`는 요청 받아서 응답 돌려주는 것만 하고, 실제 SQL은 `repositories/`에만 있게 나눠뒀어요 — 그래서 나중에 테이블 구조를 바꿀 일이 생기면 `repositories/` 안에 있는 해당 파일만 고치면 돼요. 처음엔 이렇게까지 나눌 필요가 있나 싶었는데, 기능이 하나둘 늘어나면서 `routers/posts.py` 하나에 SQL까지 다 있었으면 지금쯤 감당이 안 됐을 것 같아요.

프론트도 `index.html`(구조) / `style.css`(디자인) / `app.js`(동작)로 나눴어요. 원래는 `index.html` 하나에 다 몰아넣었었는데, 파일이 커지니까 원하는 부분 찾는 것부터 일이라 분리했어요.

**한 가지 삽질했던 부분**: CSS/JS를 고쳐서 다시 배포했는데 브라우저에는 예전 화면이 그대로 보이는 문제가 몇 번 있었어요. 알고 보니 브라우저가 `style.css`, `app.js`를 캐시해두고 재사용하는 거였고, 강력 새로고침을 해야만 반영되는 상황이었어요. 매번 사용자한테 캐시 지우라고 할 수는 없으니, `main.py`에서 파일의 마지막 수정 시각을 읽어서 `<link>`/`<script>` 주소 뒤에 `?v=1234567890`처럼 붙이는 방식으로 고쳤어요(`_asset_version()`). 파일 내용이 바뀌면 이 숫자도 자동으로 바뀌어서, 브라우저 입장에서는 "새 주소"로 보이니까 캐시를 안 쓰고 새로 받아가요.

## 기능들

### 로그인 유지 (리프레시 토큰 로테이션)

원래는 로그인하면 액세스 토큰 하나만 받고, 그게 30분 지나면 그냥 다시 로그인해야 했어요. 딱히 새로고침할 때 끊기는 건 아니었는데도 30분마다 강제 로그아웃되는 게 은근히 거슬려서, 리프레시 토큰을 따로 발급하는 방식으로 바꿨어요. 로그인하면 액세스 토큰(30분짜리)이랑 리프레시 토큰(14일짜리)을 같이 받고, 액세스 토큰이 만료돼서 API가 401을 돌려주면 프론트에서 자동으로 리프레시 토큰을 들고 `/refresh`를 호출해서 새 액세스 토큰을 받아와요. 화면에서는 그냥 "로그인이 오래 유지된다" 정도로만 보이지만, 뒤에서는 30분마다 이 과정이 조용히 일어나는 거예요.

리프레시 토큰은 쓸 때마다(=`/refresh`를 호출할 때마다) 그 토큰을 폐기하고 새 토큰을 또 발급하는 "로테이션" 방식으로 만들었어요. 하나의 리프레시 토큰은 딱 한 번만 쓸 수 있는 셈이에요. 이렇게 한 이유는, 이미 폐기됐어야 할 옛날 토큰이 다시 서버로 들어오면 "정상적인 사용이 아니라 누가 훔쳐서 같이 쓰고 있는 상황일 수 있다"고 판단할 수 있기 때문이에요 — 실제로 그런 경우엔 그 계정의 모든 로그인을 그 자리에서 강제로 끊어버리게 해뒀어요.

리프레시 토큰은 액세스 토큰(JWT)이랑 다르게 그냥 랜덤 문자열이에요. 처음엔 이것도 JWT로 만들까 했는데, 리프레시 토큰은 어차피 DB에 저장해둔 값이랑 대조해야만 유효/무효를 판단할 수 있는 구조라서(그래야 로그아웃했을 때 진짜로 무효화가 되니까) 자체적으로 서명 검증이 되는 JWT일 필요가 없더라고요. 오히려 자체 검증되는 토큰을 그대로 믿어버리면 "DB에서는 이미 지웠는데 토큰 자체는 아직 유효해 보이는" 상황이 생길 수 있어서 일부러 다르게 만들었어요. 대신 DB에는 토큰 원본이 아니라 sha256 해시만 저장해서, DB가 통째로 유출되는 최악의 상황에도 토큰을 그대로 훔쳐 쓸 수는 없게 했어요.

로그아웃을 누르면 서버에 있는 그 리프레시 토큰을 실제로 무효화시켜요. 비밀번호를 바꾸거나 관리자가 계정을 삭제할 때도 그 계정의 리프레시 토큰을 전부 끊어버리는데, 그래야 예전에 로그인해둔 다른 브라우저/기기가 그대로 로그인 상태로 남아있는 일이 없거든요. (참고로 액세스 토큰 자체는 JWT라서 만료 전엔 서버가 강제로 무효화할 방법이 없어요 — 그래서 액세스 토큰 수명은 짧게(30분) 잡고, 진짜 "로그아웃/강제 만료"의 역할은 DB에 기록이 남는 리프레시 토큰 쪽에서 맡게 만든 거예요.)

### 게시판

가장 기본이 되는 부분이에요. 글쓰기/수정/삭제, 댓글, 조회수, 검색(제목+본문), 정렬(최신순/조회수순)까지 있어요. 목록은 표+페이지네이션 레이아웃으로 만들어서, 한 페이지에 10개씩만 보여주고 백엔드에서 `LIMIT`/`OFFSET`으로 필요한 만큼만 가져와요 — 글이 아무리 쌓여도 목록 화면이 느려지지 않게요.

댓글이 달리면 글쓴이한테 헤더의 🔔 알림으로 알려줘요(내가 내 글에 단 댓글은 제외). 알림을 누르면 그 글로 바로 이동하고요. 그리고 게시글마다 👍❤️😂😮😢 이모지로 반응을 남길 수 있어요 — 같은 이모지를 또 누르면 취소되는 토글 방식인데, `post_reactions` 테이블에 `(post_id, username, emoji)` 조합을 `UNIQUE`로 걸어서 "있으면 지우고 없으면 추가"하는 식으로 구현했어요.

글 쓸 때 카테고리(자유/질문/정보/기타)도 고를 수 있고, 목록에서 카테고리별로 필터링해서 볼 수 있어요. "공지" 카테고리도 있는데 이건 관리자 계정만 고를 수 있게 서버에서 막아뒀어요 — 프론트에서 선택지 자체를 숨기는 것뿐 아니라, `POST/PUT /api/posts`에서도 관리자가 아니면 403을 돌려주게 이중으로 체크해요(관리자 페이지 접근 막을 때랑 똑같은 방식).

본문은 마크다운 문법을 일부 지원해요(굵게/기울임/인라인 코드/제목/목록/인용/링크/코드블록). 처음엔 `markdown` 같은 pip 라이브러리를 하나 더 쓸까 했는데, "사용자가 입력한 텍스트를 HTML로 바꿔서 그대로 화면에 꽂아넣는" 기능은 잘못 만들면 XSS(악성 스크립트 삽입) 구멍이 생기기 딱 좋겠더라고요. 그래서 지원할 문법 몇 개만 골라 직접 변환기를 만들었어요(`markdown_utils.py`). 원리는 단순해요 — 사용자가 입력한 글자는 태그로 감싸기 직전에 무조건 `html.escape()`를 거치게 만들어서, `<script>` 같은 걸 그대로 입력해도 화면엔 그 글자 그대로만 보이고 절대 실행되지 않게 했어요. 링크도 `http(s)://`로 시작하는 주소만 허용해서 `javascript:` 같은 위험한 스킴은 걸러내요.

### 날씨

[Open-Meteo](https://open-meteo.com)라는 무료 API에서 30분마다 자동으로 날씨를 받아와요. 회원가입도 카드 등록도 필요 없는 API라 골랐어요(돈 나갈 일이 없어야 해서요). 자동 수집 말고 사람이 직접 "오늘 몇 도였다" 하고 수동으로 기록을 남기는 것도 가능한데, 자동 기록은 🤖 뱃지, 수동 기록은 📝 뱃지로 구분해뒀어요.

원래는 이 데이터를 PostgreSQL이 아니라 MongoDB에 바로 저장했었어요. "외부 API에서 그대로 받아오는 데이터는 나중에 필드가 바뀔 수도 있으니 스키마 없는 MongoDB가 낫겠다" 싶어서 한 번 다르게 써보고 싶었거든요. 근데 나중에 게시글을 PostgreSQL → MongoDB로 백업하는 기능을 관리자 화면에 만들면서, "날씨도 이 패턴으로 통일하는 게 낫겠다"는 생각이 들었어요. 그래서 지금은 다른 데이터들이랑 똑같이 PostgreSQL(`weather_records` 테이블)에 원본을 저장하고, 10분마다 자동으로 MongoDB에 백업본을 복사해두는 구조로 바꿨어요. 게시글 백업(1시간 주기)보다 훨씬 자주 도는 이유는, 날씨는 30분마다 계속 새로 쌓이는 데이터라서 백업 주기가 너무 뜸하면 그사이 쌓인 기록 여러 개가 한꺼번에 몰려서 백업되기 때문이에요.

원래는 최근 30개까지 목록에 다 보여줬는데, 자동 수집이 30분마다 계속 쌓이다 보니 목록이 너무 길어졌어요. 그래서 메인 화면엔 최근 10개만 보여주고, "이전 기록 보기"를 누르면 게시판이랑 똑같이 페이지 넘겨가면서 전체 기록을 볼 수 있게 따로 뺐어요.

### 상품등록 및 후기

사진 + 설명 남기는 리뷰 게시판이에요. 게시판이랑 구조는 비슷한데 이미지가 들어간다는 점이 달라요. 서버 처음 켜질 때 예시 후기 5개가 자동으로 채워지는데, 캐릭터 이미지는 어디서 가져온 게 아니라 원+선 조합으로 코드에서 직접 그린 SVG예요(저작권 신경 안 써도 되게). 이미지는 파일로 안 두고 `data:image/...;base64,...` 문자열 그대로 DB 컬럼에 저장했는데, 그래서 업로드 용량을 3MB로 막아뒀어요 — 안 그러면 DB가 이미지로 계속 무거워질 것 같아서요.

### 미니게임 + 계정별 랭킹

솔직히 이건 그냥 재미로 만들었어요. 숫자야구, 두더지잡기, 색깔 기억 게임(사이먼), 반응속도 테스트 이렇게 4개가 있고, 미니게임 메뉴에 들어가면 게임 고르기 전에 **전체 랭킹**이 먼저 보여요 — 다른 계정이 뭘 몇 등 했는지 게임에 안 들어가도 바로 확인할 수 있게요.

랭킹은 게임마다 계정당 "본인 최고 기록" 딱 한 줄만 `game_scores` 테이블에 저장해요. 게임마다 좋은 점수의 방향이 달라서(숫자야구는 시도 횟수가 적을수록, 두더지잡기는 점수가 많을수록 좋은 식) `repositories/games.py`에 그 방향을 정리한 매핑을 하나 두고, 새 점수가 기존 기록보다 좋을 때만 덮어쓰게 SQL의 `ON CONFLICT ... DO UPDATE ... WHERE` 구문으로 처리했어요. 이거 처음엔 그냥 매번 덮어쓰다가, 그러면 더 못한 기록으로도 갱신돼버리는 걸 뒤늦게 알아채고 조건을 추가했어요.

### 알림 / 프로필 / 다크모드

- **알림**: 위 게시판 항목에서 설명한 댓글 알림이 헤더 종 모양 아이콘에 쌓이고, 30초마다 자동으로 새로고침돼요. "모두 읽음" 버튼도 있어요.
- **프로필 사진 + 자기소개**: "내 정보"에서 사진(2MB 이하)이랑 150자 이내 소개를 등록할 수 있어요. 등록 안 하면 기존처럼 이름 이니셜 + 자동 색상 원으로 나와요. 다른 사람 글 목록에 뜨는 아바타까지 전부 사진으로 바꾸는 건 욕심내지 않고, 헤더랑 내 정보 화면에만 적용했어요.
- **다크/라이트 모드**: 헤더 버튼으로 바로 전환되고 `localStorage`에 저장돼서 다음에 접속해도 유지돼요. CSS 변수를 다크/라이트 두 세트로 정의해두고 `<html>` 태그의 속성 하나만 바꾸는 식이라, 색상 전체가 한 번에 바뀌어요.

### 자료실 / 엑셀 출력 / 내 활동

파일 업로드/다운로드(최대 20MB), 게시글·자료실 목록 엑셀(.xlsx) 다운로드, 내가 쓴 글/댓글/올린 파일을 한 화면에 모아보는 "내 활동" 메뉴도 있어요. 파일은 실제 바이너리는 서버 디스크(도커 볼륨)에 두고, DB에는 누가 언제 뭘 올렸는지 메타데이터만 저장하는 식으로 나눴어요.

### 관리자

회원가입할 때 "일반 사용자"/"관리자로 가입" 중에 고를 수 있는데, 관리자로 가입하려면 서버에 설정된 코드(`ADMIN_SIGNUP_CODE`, 기본값 `admin1234`)를 알아야 해요. 코드가 틀리면 그냥 가입이 거부돼요. (예외로, 사이트에 회원이 정말 한 명도 없을 때 가입하는 최초 1명은 코드 없이도 자동으로 관리자가 돼요 — 관리자가 아예 없는 상황을 막기 위한 안전장치예요.) 실제로 쓸 거면 `ADMIN_SIGNUP_CODE`는 꼭 본인만 아는 값으로 바꿔야 해요.

관리자로 로그인하면 전체 회원 수/글 수/파일 수 같은 현황이랑 회원 목록을 볼 수 있고, 본인 계정 빼고 다른 계정을 삭제할 수 있어요. 권한 체크는 프론트에서 메뉴만 숨기는 게 아니라 `security.py`의 `require_admin`으로 서버에서도 한 번 더 막아둬서, API를 직접 두드려도 403이 떠요.

### PostgreSQL → MongoDB 백업

게시글과 날씨 기록, 이 두 가지를 대상으로, PostgreSQL에 있는 원본은 그대로 두고 같은 내용을 MongoDB에도 복사해두는 기능이에요. 게시글은 1시간마다, 날씨는 10분마다 자동으로 돌고, 관리자 화면에서 각각 수동으로도 바로 실행할 수 있어요. 여러 번 돌려도 중복이 안 쌓이게, PostgreSQL의 번호(`id`)를 MongoDB 문서의 `_id`로 그대로 써서 같은 데이터면 덮어쓰기만 되도록(upsert) 만들었어요. 실무에서는 운영 DB는 그대로 두고 다른 저장소에 주기적으로 복사본을 남기는 걸 백업/재해복구 목적으로 쓴다고 들었는데, 그 패턴을 단순하게 흉내내본 거예요.

두 백업 로직(`backup_sync.py`/`repositories/backup.py`, `weather_backup_sync.py`/`repositories/weather_backup.py`)은 사실상 대상 테이블만 다르고 코드 구조는 완전히 똑같아요. 처음엔 게시글용으로만 만들었다가, 날씨를 MongoDB에서 PostgreSQL로 옮기면서 백업 코드를 그대로 복사해서 대상만 바꿨어요. 지금 와서 보면 공통 로직을 함수 하나로 합칠 수도 있었을 것 같은데, 대상 테이블마다 컬럼 구조가 달라서 그냥 파일을 나눠 가져가는 쪽을 택했어요.

한 가지 아직 못 채운 부분: 이 백업들은 "새로 생기거나 바뀐 것"만 골라 보내는 게 아니라 매번 전체를 다시 복사해요. 그리고 원본에서 삭제된 데이터가 있어도 백업본에서는 안 지워져요(추가/덮어쓰기만 하지 삭제는 안 하는 구조라서요). 지금 규모에서는 문제없지만, 데이터가 훨씬 많아지면 손봐야 할 부분이에요.

## 데이터가 자꾸 초기화되던 문제

한동안 `docker compose down` 했다가 다시 `up`하면 회원가입한 계정, 써둔 글이 전부 사라지는 문제가 있었어요. 처음엔 뭐가 문제인지 몰라서 한참 헤맸는데, `docker-compose.yml`을 다시 열어보니 자료실 파일(`web` 서비스)은 `uploads_data`라는 볼륨에 연결해뒀으면서 정작 PostgreSQL(`db` 서비스)에는 볼륨 연결을 빼먹고 있었더라고요. 상품후기 캐릭터는 서버 켤 때마다 자동으로 다시 채워지는 로직이라 티가 안 났을 뿐이었어요.

컨테이너는 언제 지워져도 이상하지 않은 "일회용"에 가까운 존재라서, 데이터는 컨테이너 밖의 볼륨에 따로 둬야 컨테이너를 지웠다 새로 만들어도 안 사라져요. `pgdata`라는 볼륨을 추가해서 해결했어요:

```yaml
db:
  volumes:
    - pgdata:/var/lib/postgresql/data   # 새로 추가됨
```

참고로 `docker compose stop`(또는 `Ctrl+C`)은 컨테이너를 멈추기만 하는 거라 원래도 안전했고, 문제는 컨테이너를 아예 지우는 `down` 쪽이었어요. 이미 여러 번 `down`을 했었다면 지금부터는 안전하지만, 그 전에 만들었던 계정/글은 이미 날아갔을 수 있어요.

## 접근성 관련 신경 쓴 것들

입력창마다 `<label>`을 제대로 연결해서 스크린리더로도 뭘 입력하는 칸인지 읽히게 했고, 비밀번호 입력창엔 표시/숨김 버튼을 달았어요. 포커스 이동 시 테두리가 잘 보이게 했고, 에러/성공 메시지는 `aria-live`로 스크린리더 사용자한테도 바로 안내되게 했어요.

## 토큰은 왜 localStorage에?

액세스 토큰이랑 리프레시 토큰 둘 다 `localStorage`에 저장해서 새로고침해도 로그인이 유지돼요. 다만 이 방식은 XSS 공격에 상대적으로 취약하다고 해서, 실무에서는 `httpOnly` 쿠키를 더 권장한다고 해요. 여기서는 학습용으로 가장 단순하게 이해할 수 있는 방식을 골랐어요. (리프레시 토큰 쪽은 어차피 DB 대조 + 로테이션으로 한 번 쓰면 폐기되게 해뒀으니, 훔쳐가도 오래 못 써먹게는 만들어뒀다는 정도로 절충했어요.)

## 이번에 새로 이해하게 된 것들

- 비밀번호는 절대 그대로 저장하면 안 되고, bcrypt 같은 단방향 해시로 저장해야 DB가 통째로 유출돼도 원래 비밀번호를 알아낼 수 없다는 것
- JWT는 `{"sub": "사용자이름", "exp": 만료시각}` 같은 정보를 SECRET_KEY로 서명한 문자열일 뿐이라, 서버가 매 요청마다 DB에서 세션을 조회할 필요 없이 서명 검증만 하면 된다는 것
- FastAPI의 `Depends()`로 로그인 체크 같은 반복되는 로직을 엔드포인트 앞에 붙여서 재사용할 수 있다는 것
- SQL의 `ON CONFLICT ... DO UPDATE ... WHERE`로 "조건에 맞을 때만 갱신"하는 upsert를 한 번에 처리할 수 있다는 것
- 관계형 DB랑 NoSQL을 실제로 한 프로젝트 안에서 같이 써보니, 언제 뭘 쓰면 좋은지 감이 좀 생겼다는 것
- 액세스 토큰(JWT)은 서버가 강제로 무효화할 수 없어서, "진짜 로그아웃"을 만들려면 DB에 상태를 남기는 리프레시 토큰이 따로 필요하다는 것 — 그리고 그 리프레시 토큰도 재사용을 막는 로테이션을 걸어야 탈취당했을 때 대응할 여지가 생긴다는 것
